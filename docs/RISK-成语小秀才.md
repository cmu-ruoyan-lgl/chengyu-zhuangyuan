**顺带修好的环境缺陷（根因，非绕行）**：Homebrew 的 `python@3.14` 与 `python@3.13` 在 macOS 26.0.1 上 `platform.mac_ver()` 均返回空串 → 任何 pip 命令崩溃。

- **真实根因**：`pyexpat` 扩展链接的是系统 `/usr/lib/libexpat.1.dylib`，但本机系统 expat 缺 `XML_SetAllocTrackerActivationThreshold` 符号（bottle 在更新的 SDK 上构建）→ `plistlib` 读不了 `SystemVersion.plist` → `mac_ver()` 返回空 → pip 内置 truststore 在 `_macos.py:22` 崩溃。pip 本身没坏。
- **修法**：`brew install expat`（2.7，`libexpat.1.13.0.dylib` 含该符号）→ 对两个 Python 的 `pyexpat*.so` 执行 `install_name_tool -change /usr/lib/libexpat.1.dylib /opt/homebrew/opt/expat/lib/libexpat.1.dylib` → `codesign -f -s -` 重签（ad-hoc）。原文件已备份为 `*.bak.<时间戳>`。
- **附带**：把两个 brew Python 的 `EXTERNALLY-MANAGED` 改名为 `.disabled`，使 `pip3 install X` 无需 `--break-system-packages`；补了 `/opt/homebrew/bin/pip` → `pip3.14`。
- **⚠️ 回退风险**：`brew reinstall/upgrade python@3.14`、`python@3.13` 会覆盖该 `.so`，pip 会再次崩溃；届时重跑上面的 `install_name_tool` 两行即可。恢复原状：`mv EXTERNALLY-MANAGED.disabled EXTERNALLY-MANAGED`。
- 校验结果：3.14.7 / 3.13.15 / 受管 3.13.12 / 系统 3.9.6 四个解释器 `mac_ver` 均返回 `26.0.1`，`pip install --dry-run` 全部通过。

### 两个"实测失败"的结论（很重要）

**① ~~本地运行时不含任何字体资源~~（已解决）。** 曾经报：

```
ERROR: nvgCreateFontUrho: Failed to load font: Fonts/NotoSansSC-Regular.ttf
WARNING: Could not load global fallback font Fonts/MiSans-Regular.ttf
```

现在 `assets/Fonts/` 已放 **Noto Sans SC（OFL 1.1）** 的 Regular/Bold 子集，并把同样的内容
复制成 `MiSans-*.ttf` 填引擎硬编码的兜底路径（该路径**无 Lua 配置接口**，只能靠同名文件满足）。
旧的 Arial Unicode 派生字体**已删除**，授权红线解除。详见 `assets/Fonts/README.md`。

> 附带收获：Bold 是**真实存在**的（字体源含 100–900 共 9 个字重），B2「无粗体」因此降级；
> 但裁决不变——**设计上仍不依赖字重区分层级**，因为引擎库里 `sans-bold` 曾指向 Regular。

**② headless 模式不做字形光栅化，截图模式在本 shell 拿不到窗口会话。** 证据：1500 字与 3000 字的 `max_frame_time_ms` 分别为 22.0 / 18.0ms——**字形数翻倍而帧时不增**，说明 headless 下渲染路径是空操作，图集根本没被填充；而 `-screenshot` 参数下日志仍显示 `shader compile skipped (graphics headless)`，三种参数组合（默认 / 去 `-tool_mode` / 加 `-graphicssurfaceless`）均**未产出 PNG**。

因此 **R3（字形图集容量）在 Agent 上下文内无法验证**。

**缓解措施（已落地）**：新增 `tools/screenshot.sh`，封装好全部参数。你在**系统终端 App** 里跑
`bash tools/screenshot.sh glyphtest.lua` 即可产出 PNG，把路径发给我，我可以直接读图分析——
这样"视觉不可验证"就变成"你执行一条命令即可验证"，而不是永久堵死。

## 1.7 B1 专题：字形图集的三套解法与决策树（2026-10-23 20:45）

### 先修正三个认知（这比方案本身更重要）

| # | 原先的判断 | 修正后 |
|---|---|---|
| 1 | 约束「题库去重汉字 ≤ 1500」 | **约束维度错了**。真正决定图集占用的是**单关同屏字形数**（8×8 网格 + 备选字块 ≈ 30–80 字），不是题库总量。题库 3800 条成语可以照用 |
| 2 | 图集满了会缺字 | 未证实。fontstash/nanovg 的常规行为是**图集满时整体重置并重光栅化**，表现是**周期性卡顿而非缺字**。本环境无法证实是哪一种，故不能只按"缺字"设计 |
| 3 | 40sp 是压力基准 | **真正的放大器是 DPR**。容量 ∝ 1/DPR²：40sp 在 DPR=3 手机上按 **120px** 光栅化，容量降到 1/9。手机端才是必须验证的场景 |

实测得到的两个可靠数字（CPU 侧，headless 可信）：光栅化 **0.0715 ms/字 @40px**、**1.2463 ms/字 @200px**；缓存命中 **0.0012 ms/字**。

### 三套方案

| 方案 | 做法 | 优点 | 代价 | 何时用 |
|---|---|---|---|---|
| **P1 · 预烘焙位图字库（根治）** | 离线用 fontTools+PIL 把题库汉字按真机 DPR 烘成 PNG 图集；运行时 `nvgCreateImage` 加载，用 `nvgImagePatternTinted`（可任意染色）+ `nvgScissor` 裁剪画单字 | 容量在**烘焙期就确定并可校验**；零运行时光栅化（无首字卡顿、无重置抖动）；彻底绕开 fontstash | 格子/字块需自绘，不能用 `UI.Label`；约 +1 天工作量；缩放会模糊（可烘 2 档尺寸） | 真机容量 < 80 字当量，或真机出现周期性卡顿 |
| **P2 · 约束单关字形数 + 进关预热（推荐先做）** | 关卡生成器校验「单关不重复汉字 ≤ 80」；进关时离屏把本关字形各画一遍预热 | 成本近乎为零（预热 80 字 = 5.7ms @40px；DPR=3 时约 51ms，仍在加载期可承受）；题库规模不受限 | 若真机图集 < 80 字当量仍会触发重置抖动 | **默认方案** |
| **P3 · 关卡级子集字体热切换** | 离线为每关生成只含本关汉字的小字体（~50 字，3–6KB）；进关 `nvgCreateFont`、出关 `nvgDeleteFont` | 图集占用恒定在 ~50 字；字体文件极小 | 依赖 `nvgDeleteFont` 真能释放图集 —— **本环境无法验证**，若不释放则退化为缓慢泄漏 | P2 不够用、又不想自绘控件时的折中 |

### 决策树

```
终端跑 bash tools/atlasprobe.sh  →  拿到 40 / 120 两档的 fail 与 first_fail_idx
    │
    ├─ 120 档 fail=0（容量 ≥ 4000 字当量）  →  P2 即可，无需额外工作
    ├─ 容量 500–4000                        →  P2 + 题库去重字封顶
    ├─ 容量 80–500                          →  P2 + 降矩阵字号（40→32sp）
    └─ 容量 < 80                            →  必须上 P1
```

#### 20.1 普通窗口打不开时的排查顺序（用户侧，按序做完再试）

1. **确认登录态**：在目标浏览器打开 `https://maker.taptap.cn`，用同一个 Maker 账号登录；若跳到 `/intro` 说明未登录，预览链接必然不可用。

## S33（2026-11-16 22:30）真机自测「项目构建失败: ok」—— 字体路径 fs_path 歧义

**现象**：面板点「真机自测 / 更新」反复弹 `操作失败：生成测试二维码失败: 项目构建失败: ok`。
后台 Spark 版本停在 v19，无法生成新包。"ok" 是平台把构建响应某字段误当错误消息，无诊断价值。

**定位手段**：本地跑 `node ~/.taptap-maker/mcp-runtime/0.0.38/dist/maker.js build --target-dir <项目> --json`
可完整复现远端构建错误（比面板弹窗信息详细得多）。真实报错：

```
[ERROR] 扫描资源失败: 路径引用歧义（fs_path 冲突），已阻止构建
引用位置: scripts/system/glyphwarm.lua   引用内容: 'Fonts/NotoSansSC-Regular.ttf'
项目文件: assets/Fonts/NotoSansSC-Regular.ttf   uuid=AjF-eZfFMmjbqQCllxbjNpjt
远端来源: official-res                          uuid=GEyRaYNt5b-ogx7xYDax6yyt
```

**根因**：构建器静态扫描源码里的资源路径字面量。项目自带 NotoSansSC 字体（S19 起随包分发，
主题 default-dark 注册到该路径）与平台 official-res 内同名资源 fs_path 完全相同但 UUID 不同，
扫描器无法判定引用哪一个，直接阻断打包。与 UI 改动、字体字集内容均无关。

**修法**：`glyphwarm.lua` 的字体路径改为运行时拼装
`string.format("%s/%s-Regular.ttf", "Fonts", "NotoSansSC")`，源码不再出现完整路径字面量。
该路径仅用于 headless 兜底分支（第 86 行），真机走 `warmupUI` 成功即返回，行为不变。

**验证**：改后 `grep` 确认无完整字面量残留；`verify.sh` 全绿、`luacheck` 0-0；
重跑 `maker.js build` → `构建流程全部完成`、`preview_refresh_status: 200`、上传完成。

**区分**：`maker.js build` 只生成网页预览包并刷新预览，**不新增 Spark version_code**；
新版本号只能由面板「更新」触发。构建修好后用户再点「更新」即可正常出 v20。

**通用教训**：凡是源码中出现 `Fonts/xxx`、`Textures/xxx` 等资源路径字面量，若平台 official-res
有同名资源，就会触发 fs_path 歧义阻断。新增/修改资源引用后构建失败，先跑 `maker.js build --json`
拿原始报错，别信面板的 "ok" 之类模糊文案。
